`src/pages/opportunities/OpportunitiesPage.tsx` (`App.tsx:215`). Its view state
is plain React state, hardcoded `'board'` initial value — no localStorage /
sessionStorage, no `?view=` URL param (`searchParams` declared but unused), no
server-side preference read on load, no effect auto-applying a saved/default
view. Only post-load changes are explicit user actions: the Board/List toggle,
applying a saved view (sets `viewMode` from that view's `viewType`), and
"+ Add New Stage" in list view (switches to board because stage-creation UI
lives in board view). Changing the initial state to `'list'` therefore sets the
default for every fresh load and overrides NO saved preference — none exists.

unrouted/unimported — NOT touched.

## Pre-existing finding (NOT fixed here — out of scope, flagged for Jack)

Deal-row/card click → detail navigation is broken on `main` in BOTH views,
identically, and this task does not change it. Clicking a deal row (list) or
card (board) navigates to `/opportunities/<deal.id>`, which hits the alias
route `App.tsx:230`:
`<Route path="/opportunities/:id" element={<Navigate to="/crm/opportunities/:id" replace />} />`.
React Router's `Navigate to` does NOT interpolate params, so the browser lands
on the literal URL `/crm/opportunities/:id` (detail page with id `":id"`, no
deal shown). Verified live: `/opportunities/dl_1` → literal
`/crm/opportunities/:id`, no Q3 content; direct `/crm/opportunities/dl_1` →
correct detail page with Q3 content. The 1-line diff in this task cannot cause
this (`App.tsx` untouched; the click handlers are identical in both views).
Follow-up if Jack wants it fixed: make the row/card handlers navigate directly
to `/crm/opportunities/<id>`, or fix the alias to interpolate the param. Left
as-is per scope guardrails (default change only, no bundled fixes).
