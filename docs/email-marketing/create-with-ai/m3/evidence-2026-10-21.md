## What M3 delivers (spec §12, §13, §17, §18, §20)

- Draft generation + refine (typed instruction, whole/section), direct edit,
  undo, version history (last 10), sequence consistency check, fact_map.
- Fact validation in CODE: allowed sources = profile + Brief + user-typed
  content + earlier sequence emails. Numbers/currency/dates/URLs extracted and
  checked; unmapped facts are removed or kept with a `{{NEEDS: …}}`
  placeholder that BLOCKS sending. URL allowlist = profile booking link,
  profile website domain, user-typed URLs. Samples are style-only, never fact
  sources (M1 acceptance preserved).
- New-fact Brief-sync prompt: a direct edit that adds a fact not in the
  profile or Brief surfaces it ("Add to Brief") instead of silently dropping
  it; accepting adds it to the Brief (must_include_facts + user_added_facts).
- Review and Send: recipient picker (saved segment / smart list / list / CSV
  upload with dedupe, invalid-row rejection, and per-group exclusion counts),
  AI-suggested filter from list_hints, automated checks (blocking vs
  warnings), test send (owner addresses only), path simulator, schedule /
  send-now with idempotency key, pause / resume / cancel, locked footer
  (business name, address, unsubscribe) on every send.
- Tracking: per-recipient click links with HMAC-signed tokens (spec §20),
  UTM parameters, bot filtering (clicks ≤10s after delivery ignored —
  verified at the handler level via the signed-token path; see click tests),
  machine-open caution honored (no OPENED_NOT_CLICKED matching without a
  provider machine-open signal — M5's concern).

## Finisher repairs (the M3 job items a–b)

1. **Status anomaly (job a).** After the worker's send, the email row read
   `draft` while its campaign read `SENT`. Static analysis could NOT prove
   the single 19:57:47Z trigger (no writer sets only the email to `draft`
   without touching the draft; `generateEmail` has a draft-status guard that
   rules it out for a `scheduled` draft). Defense in depth, all in code:
   - `assertEmailEditable` (draft-generator.service.ts): every email
     mutation (refine, direct edit, undo, regenerate) is now blocked when
     the email status OR its linked campaign status is
     scheduled/sending/sent/paused. Previously refine/direct-edit blocked
     only sent/sending and undo had no guard at all.
   - `confirmSend` now refuses a fresh key on an already-launched email
     (would have created a duplicate campaign and re-sent); same-key
     double-click still replays idempotently; re-confirm after cancel is
     still allowed (fresh campaign).
   - Scheduler transitions (campaigns.service.ts, scoped to
     `kind='scheduled'` CampaignEmails so regular campaigns are unaffected):
     SENDING → linked emails `sending`; SENT → linked emails `sent`
     (before the all-failed throw, so the email agrees with its campaign
     even when every recipient failed; per-recipient outcomes live on
     CampaignRecipient). Previously NOTHING ever set a CampaignEmail to
     `sent`, so even the happy path left sent emails `scheduled` forever.
   - The worker's anomalous dev row was repaired in data only
     (`draft` → `sent` to match its SENT campaign); the code fix above is
     what prevents recurrence.
2. **HMAC-signed tracking tokens (job b, spec §20).** `trackingToken` was
   plain base64url; it is now
   `base64url(payload) + '.' + base64url(HMAC-SHA256(payload, secret))`
   over campaign/contact/email/destination, verified timing-safely in the
   click handler. Failed verification records nothing and redirects home
   (no forged clicks, no open redirect). Secret: `TRACKING_SECRET` env
   (added to `infrastructure/config/env.ts` + `.env.example`); unset → an
   ephemeral per-boot secret with a console warning (dev only; production
   must set it or tokens break across restarts). Tokenless legacy links
   keep working (the pre-existing email-send-worker flow has no tokens) —
   signing that flow is a follow-up, documented below.
3. **Direct-edit Brief-sync prompt (job b, spec §12).** Verified present,
   not re-implemented: `directEditEmail` computes `candidateNew` (claims in
   the new text that are neither allowed nor already present) and returns
   them as `newClaims`; `DraftEditor` shows the prompt with "Add to Brief".
4. **Paused emails had no launched view (found during screenshots).**
   `ReviewSend` treated only scheduled/sending/sent as launched, so a
   paused email showed the recipient picker + a confirm form that the API
   would 400. One-word fix: `paused` is now in the launched set, so a
   paused campaign shows its status plus Pause/Resume/Cancel/Refresh.
5. **Recommended-start wall clock mislabeled (found during screenshots).**
   The confirm form rendered `toLocaleString()` (browser TZ) but labeled it
   with the business TZ — on the UTC dev VM it showed "9:00 PM
   (America/Los_Angeles)" for a 2:00 PM PDT slot. Fixed to format in the
   business TZ. The underlying instant was always correct (in-window).

## Limitations (stated explicitly)

- **Live AI UNVERIFIED (capacity, not key).** Interview turns and draft
  generation return 503 "high demand" on gemini-3.8-flash (the key is
  proven valid: auth passes, zero 401/403). Fixtures/mocks verify all M3
  logic; live-AI verification must be re-run when capacity frees.
- **Real delivery UNVERIFIED.** No Gmail connection and no Resend key in
  dev: recipients fail honestly, test sends 503 honestly. The send path
  (idempotency, scheduler, pause/resume/cancel, suppression, footer,
  tracking) is verified without delivery.
- **Brief-sync prompt is session-ephemeral.** `newClaims` lives only on
  the direct-edit response, not on the email row — a reload clears the
  prompt (the kept fact itself stays in the content). Follow-up: persist
  pending newClaims on the email row.
- **Editor shows the embedded footer div as editable.** `bodyHtml`
  contains the draft footer div, and the contentEditable renders it, so a
  user can type inside the footer region; that content is footer-skipped
  by the validator and dropped at send (strip + real footer). Sends are
  correct; the UX wart is that footer-region typing silently vanishes.
  Follow-up: render footer-stripped HTML in the editor (saves already
  re-attach the footer via `ensureDraftFooter`).
- **Launched-view times render in the browser TZ** (no false label), while
  spec §18 wants business-TZ display. The confirm form now formats in the
  business TZ; the launched view is a follow-up.
- **Legacy surfaces still unsigned.** The pre-existing email-send-worker
  click links are tokenless (forgery possible for already-delivered legacy
  links) and the unsubscribe token is plain base64url. Scoped follow-ups;
  M3's own links are HMAC-signed.
- **Dev fixture notes (dev data only).** Profile booking link repaired
  `https://example.com/book` (404) → `https://example.com/` (200) so the
  send path could be exercised; the dev DB holds a VERIFIED SendingDomain
  row for `sparkling.example`, which is why domainAuth passes. The
  screenshot email ends `cancelled` (paused shot, then cancelled for the
  confirm shot); the part-2 email ends `sent` with its SENT campaign.
- **The single 19:57:47Z trigger was not proven** by static analysis (see
  repair 1). The guards + transitions prevent recurrence regardless of
  which call caused it.
