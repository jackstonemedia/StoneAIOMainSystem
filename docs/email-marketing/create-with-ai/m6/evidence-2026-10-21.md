## What changed

- **New service `api/services/email-marketing/ab-test.service.ts`** — the whole
  M6 backend, reusing the pre-existing A/B machinery instead of rewriting it:
  - `modeForCount`: <500 none, 500–1,999 split, ≥2,000 test_then_winner.
  - `assembleAbTestFromChecklist` (lenient, like M5 reactions): decision no →
    valid no-test plan; decision yes requires a resolved variable (subject or
    CTA wording), two different versions, a metric that is not opens (error:
    "opens are approximate") and not bookings (error: no booking events exist),
    wait 4–72h (default 24), test email within the sequence; missing size →
    `decide_at_send`. "Yes, skip it" parses as NO (B4a).
  - `effectiveAbMode`: Phase 8 re-check from the real recipient count; a mode
    change produces a plain-words warning reason. A "no test" decision never
    gains a mode.
  - `buildAbTestConfig`: writes the pre-existing config shape at confirm time
    (split → testPercentage 100, test_then_winner → 20, `createWithAi: true`,
    `winnerMetric: 'clicks'`, evaluationHours, subjectA/B, bodyHtmlA/B).
    `autoRollout` is NEVER set on M6 campaigns, so the old auto-rollout can
    never fire for them.
  - `evaluateWinnerRule`: the SPEC rule (unique clicks per variant, bots
    excluded): total < 20 OR relative difference < 10% → `no_clear_winner`
    (→ send A); else the higher click rate wins; ties → no_clear_winner. The
    old analytics z-test (which defaults to open rate) is left untouched for
    the old CampaignBuilder UI and is never used on this path.
  - `evaluateCampaignWinner` + `processDueAbWinners` (30s tick): split →
    outcome recorded, nothing sent; test_then_winner → `selectABTestWinner`
    flips HOLD recipients to the winner variant and sends. PAUSED skipped.
  - `getCreateWithAiResults`: computed LIVE on every read, never stored —
    delivered, bounced, unique clicks, click rate, replies (from RecipientState
    exits, since Gmail replies arrive via the poller, not EmailEvents),
    unsubscribes, complaints (always `complaintsUnavailable: true` under
    Gmail-only; the count is app-recorded COMPLAINED events only, always 0),
    approximate opens (secondary), paths buckets (exits → click-reaction →
    non-clicker follow-up → completed → received-only), A/B outcome, health.
  - `checkHealth` + `processHealthAutoPause` (30s tick): bounce warn 2% /
    auto-pause 5%; complaint warn 0.1% / auto-pause 0.3% (implemented, but
    cannot fire from real data under Gmail-only). Auto-pause uses a direct
    status update (pauseCampaign only allows SCHEDULED/SENDING, not SENT);
    pausing stops all unsent mail because the sequence runner skips PAUSED,
    the reaction tick requires status SENT, and the winner tick skips PAUSED.
  - `aiResultsSummary`: Gemini summary with validation — every number in the
    output must appear in the metrics and the output must be 2–4 sentences,
    else the numbers-only template. Generated on read, never saved.
- **Interview (`interview.service.ts`)**: Phase 6 `ab_testing` (cap 4, 8 base
  items), `ab_confirm` / `ab_confirmed` phases, `startAbTesting` /
  `confirmAbTest` (re-assembles from the saved checklist at confirm time —
  deterministic, so no transient marker is needed, unlike M5), escape-hatch
  `ab_confirmed` branch (locks from facts; omits the reactions ruleCount,
  which the pure function cannot query), `reopenPhase` clears `plan` when
  reopening to a phase before Phase 6, `generateEmail` guard accepts
  `ab_confirmed` (keeps `reactions_confirmed` for M5-era drafts). Routing:
  `reactions_confirmed` now leads to Phase 6 (messages updated), `ab_confirmed`
  leads to drafting (Phase 7).
- **Send orchestration (`send-orchestration.service.ts`)**: `runSendChecks`
  gains the A/B block (mode re-check warning; test-email-only gating; test
  email > 1 → BLOCKING; subject test where picked subject equals variant B →
  BLOCKING; CTA test where variant-A wording is absent from the body →
  BLOCKING; test_then_winner wait end after a sequence deadline → BLOCKING).
  `confirmSend` writes `abTestConfig` for Email-1 A/B campaigns only (picked
  subject becomes version A; CTA bodies via `buildCtaVariantBody`).
- **Routes**: `start-ab-testing`, `confirm-plan`, `plan`, `campaigns/:id/results`,
  `campaigns/:id/results-summary`, `campaigns/:id/evaluate-winner` (manual
  override; refuses non-testing campaigns). Tick wiring adds
  `processDueAbWinners` + `processHealthAutoPause` after reaction + sequence.
- **Frontend**: copy (banner, opening, 8 examples, plan prompt), API client
  (`startAbTesting`, `confirmPlan`, `getPlan`, `getCampaignResults`,
  `getResultsSummary`, `evaluateWinner`, `SendChecksState.abTest`),
  `InterviewChat` (Phase 6 pill, plan-confirmation banner/input),
  `InterviewFlow` (Phase 6 entry card, `needsAbEntry`), new
  `CampaignResults.tsx` (metrics, paths, A/B outcome + "Evaluate winner now"

## Bug found and fixed during live verification (not in the unit tests)

`evaluateCampaignWinner`'s test_then_winner branch called
`selectABTestWinner` (which sets winnerVariant + status completed + decidedAt)
and then overwrote `abTestConfig` with the STALE pre-decision object, wiping
the decision, leaving the campaign "testing", and letting the next tick decide
a second time (duplicate notification observed). Fixed by re-reading the
campaign after `selectABTestWinner` and adding winnerRule/winnerCounts to the
fresh config. Re-verified live: winnerVariant + completed status + results
winner + exactly one notification per campaign.

## Deviations / known limitations

- A/B testing applies to Email 1 only (spec B4 tests Email 1 only). A plan
  naming a later sequence email is a BLOCKING Phase 8 item, not a silent
  downgrade.
- The old analytics z-test (open-rate default) is deliberately left in place
  for the old CampaignBuilder UI; the Create-with-AI path never uses it.
- Complaint thresholds are implemented but cannot fire from real data under
  Gmail-only (Gmail does not notify senders of spam complaints). Mitigation:
  unsubscribe link in every email, bounce suppression, engagement monitoring.
- Real delivery UNVERIFIED (no Gmail connection in dev): winner rollout is
  verified to the HOLD-flip + config-update point; sends fail honestly
  without Gmail. App-transport gap unchanged (dev app key stub → app AI 503 +
  saved; results-summary falls back to the numbers-only template).
- No results or learnings are stored for reuse: results are computed live on
  every read; the only campaign→profile path is the user-initiated
  "Save as a good example" button. Code-reviewed, no campaign data feeds the
  next campaign's interview, Brief, or Plan.
- The A/B box renders the internal mode ids (planned test_then_winner,
  effective split) alongside the plain-words warning; the warning above it
  states the change in full sentences.

## Test script for Jack

1. Open Email Marketing → Create with AI, confirm the profile, and run the
   interview through Phase 6. Answer "yes, let's test" with a subject test,
   two different subjects, clicks as the metric, 24 hours.
2. At the plan confirmation, type "looks good" and confirm the plan locks
   (version 1) with the timeline and test branches.
3. Draft Email 1, pick a subject, go to Review and Send, pick a list, and run
   checks: with a list under 500 the A/B box says no test; 500–1,999 says
   split; 2,000+ says test-then-winner. A planned test-then-winner with a
   real list of 800 warns that the mode changed to split.
4. After sending, open the campaign's Results: delivered, clicks, click rate,
   replies, unsubscribes, approximate opens, and the A/B outcome. With a
   testing campaign, "Evaluate winner now" decides immediately.
5. Expected: winner by clicks only (never opens); fewer than 20 total clicks
   or under 10% difference → "no clear winner" and version A goes out.
