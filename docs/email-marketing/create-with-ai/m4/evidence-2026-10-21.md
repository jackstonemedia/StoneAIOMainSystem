## What changed

### Summary
Phase 4 (Sequence and Timing) is built end to end: the interview plans a
sequence (how many emails, over how many days, what each one is for, start,
deadline, send-time prefs), the draft generates all sequence emails, one
Phase 8 confirm launches the whole sequence, and a runner sends later emails
automatically per recipient — timed from when EACH person got Email 1, not
from a campaign clock. Guards (exits, suppression, frequency cap, conflict,
deadline, pause/cancel) are enforced in code before every send.

## How it works
1. Brief confirmed → Phase 4 entry card → "Continue to Sequence and
   Timing" → sequence interview (max 4 questions) → sequence confirmed
   (timeline + compression note shown) → drafting (Phase 7).
2. A 1-email sequence answer keeps the M3 single-email flow exactly.
3. Phase 7 generates all sequence emails (later emails build on earlier
   ones). Phase 8 (SequenceReview): pick recipients once (CSV), run checks
   per email, confirm-all → Email 1 launches via the standard send path;
   emails 2..N are scheduled (no campaigns of their own).
4. When Email 1's campaign reaches SENT, recipients enroll into
   RecipientStates with per-person dues from their actual sent times.
5. Every 30s the runner advances due steps: guards re-checked, then each
   due email sends via Gmail (rendered per recipient), recorded as a
   SENT EmailEvent, and the state advances to the next step (or completes /
   skips on deadline). Pause/cancel stops everything unsent.

## Deviations (stated plainly)
- **Auto-send, not manual per-email confirms.** The pre-existing engine
  header note said later emails go through "the normal Phase 8 confirm
  path." M4 deliberately deviates: later sequence emails send AUTOMATICALLY
  via the runner. Rationale: the sequence was approved as a whole in Phase
  8, so whole-sequence approval satisfies the approval rule, and manual
  per-email babysitting contradicts what "sequence" means. If Jack wants
  manual steps, that is a follow-up decision, not a silent change. The
  engine's header + advance/record doc comments were corrected to match.
- **Per-person timing requires per-contact sends.** Different dues per
  contact cannot share one campaign send time, so later emails are sent
  per contact (not via a campaign send), with the email-1 campaign's id
  used for tracking UTM + EmailEvent campaignId.
- **Deadline compression is date-granular.** A compressed plan's last
  email lands ON the deadline date at the window time (08:00), even if that
  instant is after a deadline instant earlier the same day. The deadline
  rule ("nothing after the deadline") is enforced at the date level by
  the compression, and at the instant level by the per-person schedule
  block (past-deadline slots → null + "Would fall after the deadline.").
- **Window parser quirk (pre-existing, not fixed in M4).** The send-window
  parser turns an ambiguous "weekdays 8 to 5" (no am/pm) into 05:00–08:00
  (it sorts the two numbers). Tests use unambiguous "8am to 5pm" (→ 8–17).
  Fixing the parser is follow-up work, not M4 scope.
- **Single-email-sequence behavior change vs the M3 test script.** A draft
  that answers "one email" in Phase 4 now carries a 1-email sequence object
  and flows through the sequence-confirmed path (DraftReviewFlow's
  multi-email branch only triggers when count > 1, so the UI is unchanged
  for 1-email campaigns; the draft state now has a sequence object where
  M3 drafts had none).

## Limitations (stated explicitly)
- **App-transport gap (unchanged from M3).** The connector proves prompt +
  schema + model + key + capacity (live interview + drafting proven via
  the connector for M2/M3). The APP server still reads its own env key
  (dev `.env` stub → app-level 'AI not configured' 503, `/ready` ai:false).
  Live verification THROUGH THE APP's `/turn` / generate endpoints is NOT
  possible until a real key is in the app's env. Turns fail honestly with
  503 + `saved:true` (answers are saved before the AI call). Do NOT touch
  dev `.env` stubs; never print, store, or commit anything key-like.
- **Real delivery UNVERIFIED (no Gmail connection in dev).** Email 1's
  recipients fail honestly ("No active Gmail connection"); the runner's
  sends were verified with an injected sender + simulated SENT recipients
  (labeled as such). Nothing here claims real delivery.
- **Complaint gap (Gmail-only, no equivalent).** Gmail does not notify
  senders of spam complaints for API-sent mail, so complaint-based alerts
  and auto-pause cannot fire from real data under Gmail-only. Stated in
  every milestone update, not hidden. Bounce suppression via Gmail mailbox
  parsing is M5 scope.
- **Live DNS owed.** Real-domain DNS re-verification from an environment
  with DNS access is still owed (this VM blocks raw UDP/53; the reserved
  dev domain `sparkling.example` uses the sending-domain row fallback, not
  live DNS). The DMARC warning fires correctly (warn, not block) for the
  dev domain.
- **Launched-view times render in browser TZ** (the M4 launched screenshot
  shows "11/2/2026, 4:00:00 PM" — browser TZ, not business TZ). Spec §18
  wants business-TZ display; the confirm form was fixed in M3, the launched
  view is follow-up (same wart as M3).
- **Legacy unsigned surfaces (unchanged from M3).** Pre-existing worker
  click links stay tokenless; the unsubscribe token stays plain base64url.
  M4's own links (via `renderFinalHtml`) are HMAC-signed. Scoped follow-ups.
- **Session-ephemeral newClaims (unchanged from M3).** The Brief-sync
  prompt's `newClaims` live only on the direct-edit response, not persisted
  — reload clears the prompt, the kept fact stays in content. Follow-up:
  persist pending newClaims on the email row.
- **Editor footer-div wart (unchanged from M3).** The editor shows the
  embedded footer div as editable; footer-region typing is footer-skipped
  by the validator and dropped at send (sends correct, UX wart). Follow-up:
  render footer-stripped HTML in the editor.
- **Test-send switch landed (commit `8bf9fc2`) + no-Resend alignment
  (`5ba7812`).** Test sends go through Gmail (honest 503 when unconnected);
  domain checks use direct DNS; the Resend webhook is deleted; env keys
  removed. The `resend` npm package removal waits for final completion
  (code uses go first; the package is harmless while unused).
- **NO-RESEND CORRECTION (appended here, not rewriting history).** The
  posted M3 row block predates the Gmail-only decision. The full amendment:
  the build is Gmail-only (no Resend account, key, package use, or webhook
  anywhere); campaigns send via the Gmail channel; domain SPF/DKIM/DMARC
  via direct DNS; opens/clicks via the app's own tracking; unsubscribes via
  the app's own link; bounce suppression via Gmail mailbox parsing (M5
  scope); complaint webhooks have NO Gmail equivalent (see complaint gap
  above). Never ask Jack for a Resend key; it is moot.
