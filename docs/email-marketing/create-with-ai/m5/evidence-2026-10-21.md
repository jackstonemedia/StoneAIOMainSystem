## Deviations (stated plainly)

- OPENED_NOT_CLICKED is NOT creatable (see above) — the spec's own §22
  default 17 says disable it when the provider cannot distinguish machine
  opens, and under Gmail-only app tracking the open pixel is campaign-
  level, so opens cannot be attributed to one email. NOT_CLICKED is the
  reliable replacement.
- CLICKED_NOT_ACTED is NOT creatable (no booking events exist — dependency
  D1 from M0). CLICKED_NOT_REPLIED covers the reply-tracked case.
- NOT_OPENED follows the spec's literal §10.1 definition ("no open events
  at all" in the window) and is therefore campaign-level by design.
- Reaction send timing: a click rule's pending send is scheduled at
  tick time + delay (not click time + delay). With the 30s live tick the
  difference is under a minute; for backlogged ticks it means the reaction
  goes out delay-after-detection rather than instantly as overdue.
- Simulator approximation (unchanged from design): windows are evaluated
  at the end of the timeline, not chronologically interleaved, so a click
  arriving after the window end would fire the click rule in the simulator
  while the live tick would have fired the window rule first. None of the
  7 canonical scenarios contains a late click, so it never affects them.
- Tag actions write BOTH the Tag row (workspace tag list) and the
  contact's `tagsJson` array, because Contact has no relation to Tag
  (tags live in `tagsJson`, which ContactDetail reads).
- Soft-bounce "3 consecutive" is read as 3 soft bounces for the same
  contact within 30 days (documented simplification).
- The late-click guard for window-evaluated sources (a later click must
  not reopen a decided source) is code-reviewed and unit-consistent but
  NOT live-verified: it only matters for multi-email campaigns, and the
  M5 fixture is single-email. The primary paths are all live-verified.
- Pre-existing progress-bar quirk NOT fixed in M5 (out of scope): once
  the Brief is confirmed, all phase pills show done. Visible in the
  interview screenshot (Phases 1–4 checked while on Phase 5).
- Campaign event counts in the paths screenshot (BOUNCED 4, SENT 8)
  include duplicate fixture SENTs from the repeated tick-script runs
  (cleaned for bob only, the tick subject). Dev-fixture data, not app
  data — the live paths themselves (alice / bob) are the verified result.

## Known limitations (honest)

- App-transport gap (unchanged since M2): the dev app key is a stub, so
  app interview turns / generation return the app's own 503 "AI is not
  configured" path (answers still saved). The connector key proves the
  prompt, schema, model, and capacity; live AI through the app itself is
  still unverified until the app runs with a real key.
- Real delivery UNVERIFIED: no Gmail connection in dev. Reaction sends
  were verified with an injected sender + simulated events (labeled as
  such above); the live 30s tick's Gmail path is the same
  `sendGmailMessage` path M3/M4 verified to the point of the honest
  "No active Gmail connection" failure.
- Complaint gap (Gmail-only, stated to Jack 2026-10-21): Gmail has no
  spam-complaint notification equivalent, so complaint-rate health alerts
  cannot fire from real data. Mitigation: the unsubscribe link in every
  email, plus bounce and engagement monitoring. Complaint exits still work
  when a complaint is recorded through the app's own unsubscribe / abuse
  paths.
- Bounce mapping falls back to a recency heuristic when no Message-ID is
  present (documented); exact mapping works when the DSN carries one.
- Reaction email bodies for click rules come from Phase 7 generation:
  rules arm only after the Phase 8 check passes (no undrafted reaction
  email can send).
